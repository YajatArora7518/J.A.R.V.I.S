# Video reference upgrade — 6 October 2026

The provided video was inspected locally using sampled frames. Its filmed laptop UI shows a dark background, cyan spherical reactor, narrow activity rail and conversation beneath/alongside it. The implementation follows that visual direction; it is not a pixel-perfect reconstruction. The video's third-party task/contact subtitles were reference material only. No recipient from the video was contacted. Audio was not transcribed.

## Implemented

- Animated organic cyan wire sphere and white glow; state/audio response preserved. Large telemetry panels moved into a Controls drawer, with a narrow rail for actions, actual saved tasks and microphone status. Existing bridge IDs and fallbacks retained. Initial clock/battery/CPU placeholders no longer show invented historical values.
- Readable, copyable multiline conversation; task rows use literal text and display up to twelve saved pending items. Owner/title survive local persistence. `assign <task> to <name>` and `<name> ko <task> assign karo` save a local assignment explicitly without claiming a notification. Distinct longer task titles are not silently overwritten by assignment substring matches. Unclear completion requests ask for the title rather than claiming the first task completed.
- Shared natural Hinglish and reasoned-disagreement rules across live/cloud/local conversation prompts. Complete drafts and explanations are allowed; ordinary acknowledgements remain concise. Current claims require real source results, uncertainty is stated, and actions require actual results.
- Email/message/letter drafting routes to a complete chat artifact rather than typing into the active application. Drafts use a reply-writing prompt without extra stored personal context and a larger output budget; the budget survives cloud-to-local fallback. A generated draft is never delivery verification.
- Laptop shutdown/restart use a single voice/chat confirmation flow. Exact requests are distinguished from discussion, email content and closing an app. Confirmation expires in 30 seconds, cancel stops the pending request, and unrelated new commands invalidate it. The native Windows adapter uses a ten-second delay without forced app closure; OS rejection is preserved and acceptance is not misreported as a verified power transition.
- Registry static risk cannot downgrade higher risk implied by the actual tool parameters. Other high-risk tools retain their existing security dialog/authorization behavior; this change does not make all such prompts conversational.
- Fixed WhatsApp English recipient parsing (`send Rahul a WhatsApp message saying ...`) and prefixed Hinglish follow-ups (`ab usko bol ...`) while preserving exact message text and requiring recent verified recipient context. Messaging and call attempts still cannot be silently retried after uncertain submission.
- New **Talk to Jarvis** button explicitly arms one utterance for 15 seconds when the mic is enabled. It respects mute and does not weaken the wake-name/background-speech filter. Normal voice use remains `Jarvis` followed by a command.
- A requested power confirmation admits only exact affirmative/cancel voice replies without repeating the wake name, during its 30-second validity. An unrelated sentence is still rejected. Speech `stop` also clears a pending power request.
- The observed transcription spelling `Jervis` is accepted at the start of an utterance and stripped only from the command prefix. Mentioning it elsewhere or saying `jueves` does not activate the normal address gate; message contents retain their exact spelling.
- An unresolved planner cannot return a successful completion report; registered-tool steps retain their actual success and verification.

## Practical limits

This is a capable laptop assistant, not an unrestricted fictional agent. Account login, changing app layouts, exact recipient resolution, network/provider availability and OS permission remain real dependencies. Natural tone and disagreement were improved in prompts; only the recorded live exchange establishes current spoken behavior. Incoming-call answering and every Discord/Instagram/native WhatsApp sending or call path have not received new real-world acceptance in this upgrade. No outgoing message/call or actual shutdown/restart was performed. Earlier Divyansh test approvals were not reused to resend anything. Ollama is currently unavailable; the running assistant uses its configured hybrid/cloud connection. Task assignment saves locally; sending the person a notification requires an explicitly addressed communication command.

Use `docs/JARVIS_USE_GUIDE.md` for voice/chat commands. Existing personal files, tasks, contacts and prior modifications were preserved.
